    Clase 4: DTOs vs Entities - La diferencia clave¶

    En esta clase entenderemos por qué usamos DTOs separados de las Entities, y los 3 niveles de validación.

    El Problema: ¿Por qué no usar la Entity directamente?¶

    Imaginemos nuestra Entity User:

    @Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String email;
    private String password;
    private String passwordSalt;
    private LocalDateTime createdAt;
    private boolean active;

    @ManyToMany
    private List<Role> roles;

    // Getters y setters
}

    Problemas de exponer la Entity directamente¶

    Problema Ejemplo Consecuencia
    Exponer datos sensibles El cliente recibe password en JSON Security breach
    Recibir campos inválidos Cliente envía id en POST Sobreescribir IDs
    Relaciones problemáticas List<Role> causa N+1 queries Problemas de rendimiento
    Acoplamiento Cambios en DB rompen la API Menor flexibilidad

    La Solución: DTOs¶

    Un DTO (Data Transfer Object) controla exactamente qué datos entran y salen.

    Request DTO - Lo que el cliente puede enviar¶

    public record CreateUserRequest(
    String name,
    String email,
    String password
) {}

// El cliente NO puede enviar: id, passwordSalt, createdAt, roles

    Response DTO - Lo que el cliente recibe¶

    public record UserResponse(
    Long id,
    String name,
    String email
) {}

// El cliente NO ve: password, passwordSalt, roles

    Los 3 Niveles de Validación¶

    Cada capa valida algo diferente:

    Capa Qué valida Cuándo se ejecuta Propósito
    DTO Formato de datos Por API (con @Valid) Mensajes claros al usuario
    Service Reglas de negocio Siempre Lógica de la aplicación
    Entity Restricciones de DB Siempre Seguridad de la tabla

    1. Entity - Validación de la Base de Datos¶

    Restricciones físicas de la tabla:

    @Entity
public class User {
    @Column(length = 100, nullable = false)
    private String name;

    @Column(length = 150, nullable = false, unique = true)
    private String email;
}

    Propósito: Si alguien bypasshea el DTO y envía 1000 caracteres, la DB lo rechaza.

    2. DTO - Validaciones de Formato (Anotaciones)¶

    Las validaciones de formato van en el DTO usando Bean Validation. Esto da mensajes claros al usuario.

    Dependencia necesaria¶

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

    Anotaciones disponibles¶

    Anotación Ejemplo Qué valida
    @NotNull @NotNull String name No puede ser null
    @NotBlank @NotBlank String name No puede ser null ni vacío
    @NotEmpty @NotEmpty String name No puede ser null ni vacío (también listas)
    @Size @Size(min=2, max=100) String name Longitud entre min y max
    @Email @Email String email Formato de email válido
    @Pattern @Pattern(regexp = "...") String telefono Expresión regular
    @Min @Min(0) Integer edad Valor mínimo
    @Max @Max(120) Integer edad Valor máximo
    @Positive @Positive Double precio Número positivo
    @Negative @Negative Integer deuda Número negativo
    @Past @Past Date fechaNac Fecha en el pasado
    @Future @Future Date fechaExpiracion Fecha en el futuro
    @Digits @Digits(integer=2, fraction=2) Double precio Dígitos enteros y decimales

    Ejemplos prácticos¶

    public record CreateUserRequest(
    @NotBlank(message = "El nombre es obligatorio")
    @Size(min = 2, max = 100, message = "El nombre debe tener entre 2 y 100 caracteres")
    String name,

    @NotBlank(message = "El email es obligatorio")
    @Email(message = "El email debe tener formato válido")
    String email,

    @NotBlank(message = "La contraseña es obligatoria")
    @Size(min = 8, max = 50, message = "La contraseña debe tener entre 8 y 50 caracteres")
    String password
) {}

    public record CreateArticleRequest(
    @NotBlank(message = "El título es obligatorio")
    @Size(min = 5, max = 200, message = "El título debe tener entre 5 y 200 caracteres")
    String title,

    @NotBlank(message = "El contenido es obligatorio")
    String content,

    @NotNull(message = "El autor es obligatorio")
    Long authorId
) {}

    public record UpdateProfileRequest(
    @Size(min = 2, max = 100) String name,
    @Email String email,
    @Pattern(regexp = "^\\+?[0-9]{10,15}$", message = "Teléfono inválido") String phone,
    @Min(0) @Max(120) Integer age
) {}

    Usar @Valid en el Controller¶

    @PostMapping
public ResponseEntity<UserResponse> create(@Valid @RequestBody CreateUserRequest request) {
    // Spring valida automáticamente antes de entrar al método
    // Si falla, devuelve 400 Bad Request con los mensajes
    User user = userService.register(request.name(), request.email(), request.password());
    return ResponseEntity.status(HttpStatus.CREATED).body(DtoMapper.toUserResponse(user));
}

    3. Service - Validación de Reglas de Negocio¶

    El Service valida lo que solo puede saberse consultando la base de datos:

    public User register(String name, String email, String password) {
    // ⚠️ Esta validación SOLO puede estar en Service
    // Requiere acceder a la DB para saber si el email existe
    if (userRepository.existsByEmail(email)) {
        throw new IllegalArgumentException("El email ya está registrado");
    }

    User user = new User(name, email, password);
    return userRepository.save(user);
}

    Flujo completo¶

    Usuario envía JSON por API
        ↓
DTO valida con @Valid (@NotBlank, @Size, @Email, etc.)
   Si falla → 400 Bad Request con mensaje claro
        ↓
Service valida negocio (email único, permisos, etc.)
   "¿Ya existe?" → "El email ya está registrado"
        ↓
Entity/DB valida restricciones finales
   "¿Más de 100 chars?" → ERROR de la DB

    Ejemplo completo¶

    DTOs con validaciones¶

    public record CreateUserRequest(
    @NotBlank(message = "El nombre es obligatorio")
    @Size(min = 2, max = 100, message = "El nombre debe tener entre 2 y 100 caracteres")
    String name,

    @NotBlank(message = "El email es obligatorio")
    @Email(message = "El email debe tener formato válido")
    String email,

    @NotBlank(message = "La contraseña es obligatoria")
    @Size(min = 8, max = 50, message = "La contraseña debe tener entre 8 y 50 caracteres")
    String password
) {}

    Controller con @Valid¶

    @PostMapping
public ResponseEntity<UserResponse> create(@Valid @RequestBody CreateUserRequest request) {
    User user = userService.register(request.name(), request.email(), request.password());
    return ResponseEntity.status(HttpStatus.CREATED).body(DtoMapper.toUserResponse(user));
}

    Service solo con lógica de negocio¶

    public User register(String name, String email, String password) {
    // Solo validaciones de negocio
    if (userRepository.existsByEmail(email)) {
        throw new IllegalArgumentException("El email ya está registrado");
    }

    // El formato ya fue validado por el DTO
    User user = new User(name, email, password);
    return userRepository.save(user);
}

    Por qué dos lugares para validar?¶

    Capa Qué validamos Ejemplo
    DTO (@Valid) Formato de los datos "¿Tiene @?" "¿Entre 2 y 100?"
    Service Reglas de negocio "¿Ya existe el email?"

    Son complementarias: - DTO: Da mensajes claros al usuario - Service: Acceso a la DB para reglas de negocio - Entity: Backup final de seguridad

    Resumen¶

    1. DTO → Validaciones de formato con anotaciones (@NotBlank, @Size, @Email, etc.)
    2. Controller → Usa @Valid para activar la validación del DTO
    3. Service → Solo validaciones de negocio (email único, permisos, etc.)
    4. Entity → Restricciones de la DB como backup
