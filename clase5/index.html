    📚 Clase: Metodología Agile + Diseño de APIs por Capas¶

    🧠 PARTE 1: METODOLOGÍA AGILE¶

    ¿Qué es Agile?¶

    Agile es una forma de trabajar donde:

    No intentamos definir todo desde el inicio, sino que construimos, probamos y ajustamos constantemente.

    🔁 Ciclo de vida en Agile¶

    1. Visualizar → definir la idea general
    2. Especular → pensar qué se necesita (backlog)
    3. Plan de ejecución → decidir qué hacer ahora
    4. Explorar → desarrollar
    5. Tareas finalizadas → tener algo funcionando
    6. Adaptarse → recibir feedback y ajustar
    7. Cerrar → entregar producto final

    💡 Idea clave¶

    Construir → probar → ajustar → repetir

    🧑‍💻 Agile en la vida real¶

    • Cliente pide algo
    • Se divide en tareas
    • Se desarrolla en iteraciones
    • Se entrega algo funcional (aunque no perfecto)
    • Se recibe feedback
    • Se cambia el rumbo si hace falta

    🔍 Code Review vs Adaptación¶

    Code Review¶

    • Detecta bugs
    • Mejora calidad del código
    • Es técnico

    👉 Ej: “esto rompe si el campo está vacío”

    Adaptación¶

    • Cambia el producto o dirección
    • Es a nivel negocio

    👉 Ej: “mejor hacer login con Google”

    🎯 Diferencia clave¶

    El code review mejora el código. La adaptación cambia lo que estamos construyendo.

    La base de datos no define la aplicación. La aplicación define la base de datos.

    🧠 Flujo correcto para crear una API¶

    1. Contexto / problema¶

    • ¿Qué queremos construir?
    • ¿Quién lo usa?

    2. Modelo de dominio¶

    Definimos entidades del negocio:

    User Course Booking

    3. Casos de uso¶

    Qué puede hacer el usuario:

    RegisterUser LoginUser BookClass CancelBooking

    4. Endpoints (API)¶

    Cómo se expone:

    POST /users/register POST /auth/login POST /bookings

    5. Services (lógica de negocio)¶

    Contienen:

    • Validaciones
    • Reglas
    • Orquestación Orquestar es coordinar varias acciones para que juntas logren un objetivo. Es cuando un service organiza varios pasos para completar una operación. Es donde se determina la responsabilidad del service

    Ejemplo:

    BookingService - createBooking() - cancelBooking()

    6. Repositories (acceso a datos)¶

    Encargados de:

    • Persistencia
    • Acceso a datos
    • Sin lógica de negocio

    Ejemplo:

    BookingRepository - save() - findByUserId()

    7. Base de datos¶

    Implementación técnica de los datos.

    🧩 Arquitectura por capas¶

    [ Controller / Endpoint ] ↓ [ Service (Use Case) ] ↓ [ Repository ] ↓ [ Database ]

    🧠 Dominio vs Base de Datos¶

    Modelo de dominio (conceptual)¶

    Booking - userId - courseId

    Modelo de base de datos (implementación)¶

    bookings ( id, user_id, course_id )

    🎯 Idea clave¶

    Primero definimos qué datos necesitamos. Después vemos cómo guardarlos.

    ⚠️ Errores comunes¶

    ❌ Diseñar desde la base de datos¶

    • lógica acoplada
    • difícil de cambiar

    ❌ Services tipo CRUD¶

    UserService - create - update - delete

    ✅ Mejor: orientado a casos de uso¶

    AuthService - login - register

    BookingService - bookClass - cancelBooking

    🔥 Concepto avanzado¶

    Repository como interfaz¶

    interface BookingRepository { save(booking) findByUser(userId) }

    Implementaciones:

    SqlBookingRepository MongoBookingRepository

    🎯 CONCLUSIÓN FINAL¶

    • Agile = adaptarse constantemente
    • Code review ≠ adaptación
    • Diseño de API = del problema hacia la implementación
    • Dominio primero, base de datos después
    • Services representan el negocio, no la DB
