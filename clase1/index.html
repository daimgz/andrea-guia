    Clase 1: Estructura Entity-Repository-Service-Controller en Spring¶

    En esta clase veremos una arquitectura típica por capas, utilizada para separar correctamente las responsabilidades relacionadas con el acceso y la gestión de la información en una base de datos. Este enfoque puede aplicarse tanto al desarrollo de una API como al backend de una aplicación en general. El punto de organizarlo de esta manera, facilita muchas cosas en el desarrollo.

    1. En caso de que ocurra un bug, podés saber con más precisión en qué parte del código se encuentra, al ser un circuito tan lineal y predecible.
    2. Al tener más consciencia del código es más fácil tener más seguridad y establecer protocolos concretos en el acceso a la información.
    3. En caso de estar trabajando en un equipo grande, facilita mucho dividir las responsabilidades.
    4. Permite escalar el proyecto sin que el código se vuelva un desorden difícil de mantener.
    5. Hace que cada clase tenga una única responsabilidad clara, evitando que todo termine mezclado.
    6. Facilita el testing, ya que cada capa puede probarse de forma aislada.
    7. Reduce el acoplamiento entre componentes, haciendo que los cambios impacten lo menos posible.
    8. Permite reemplazar implementaciones (por ejemplo cambiar la DB) sin modificar la lógica principal.
    9. Hace que el flujo de datos sea más predecible y fácil de entender para nuevos desarrolladores.
    10. Obliga a pensar antes de programar, ya que cada decisión tiene que respetar la estructura.
    11. Mejora la mantenibilidad a largo plazo del proyecto.
    12. Hace que el código sea más profesional y más alineado con estándares reales de la industria.

    Ejemplo de estructura general de las capas.¶

    Tabla: users¶

    Nombre Tipo
    id bigint (PK, auto_increment)
    name varchar(100)
    email varchar(150) (unique)
    password varchar(255)
    created_at timestamp

    Notas:

    • id → Clave primaria.
    • email → Debería tener restricción UNIQUE.
    • password → Se recomienda almacenar hash (ej: bcrypt).
    • created_at → Fecha de creación del registro.

    Tabla: articles¶

    Nombre Tipo
    id bigint (PK, auto_increment)
    title varchar(200)
    content text
    author_id bigint (FK → users.id)
    created_at timestamp

    Notas:

    • id → Clave primaria.
    • author_id → Clave foránea que referencia users.id.
    • Relación: Un User puede tener muchos Article (1:N).
    • content → Tipo text para contenido largo.

    Relación entre tablas¶

    users (1) ─────── (N) articles

    • articles.author_id referencia users.id

    Responsabilidad¶

    🏗️ Entity¶

    Representan tablas de la DB

    Representa las tablas de la DB y, por ende, se encarga únicamente de guardar la información de las mismas. En caso de haber tablas relacionadas, dependiendo del contexto se almacena directamente en la entity o no. Estos casos de uso los iremos viendo en el futuro.

    🗄️ Repository¶

    Acceso a datos (DAO)

    Se encarga de acceder a los datos, ya sea de un JSON, una DB o de la fuente que sea. Debido a tu nivel de conocimientos en SQL y al hecho de que la clase quiero que sea lo más trasladable al trabajo, utilizaremos un ORM llamado JPA. Esto hace que la mayoría de las consultas sean bastante más simples de escribir, y deja las consultas SQL solo para casos muy específicos. El funcionamiento de JPA lo veremos en clases posteriores, pero por ahora te mostraré las convenciones de los nombres de las funciones en las consultas.

    ⚙️ Service¶

    Lógica de negocio

    Acá iría lo que se conoce como "lógica de negocio". De hecho, en inglés a la capa service se la conoce también como la "business layer". Acá iría todo tipo de validaciones que sean necesarias antes de la consulta a la DB. Esto se hace principalmente por 4 razones.

    1. Tener total conocimiento de qué se está validando en cada consulta.
    2. Aumentar la eficiencia del programa al no tener que hacer una consulta innecesaria a la DB.
    3. Poder tener un throw personalizado para cada tipo de error.
    4. Facilitar el testing unitario.

    🎮 Controller¶

    Endpoints HTTP/interacción con el usuario

    El controller se encarga de recibir las solicitudes HTTP y responderlas con los response correspondientes. En caso de que lo que estamos haciendo es una GUI en vez de una API, el controller se encargaría de enviar y recibir señales de la interfaz gráfica.

    🔗 Conexión¶

    No todas las capas pueden tener acceso entre sí. Ya que cada una al cumplir una responsabilidad concreta, puede ser accedido por la capa que lo necesita. Y de esta manera mantenemos limpio el acceso.

    🏗️ Entity¶

    Puede ser accedido por cualquiera de las capas. Al representar a una tabla de la DB se comporta como un "transporte" para la información que consultamos, y por ende va a necesitar ser accedido desde cualquier lado.

    🗄️ Repository¶

    Solo puede ser accedido por la capa service y es la única que puede consultar a la base de datos. Así nos evitamos consultas distribuidas por todo el código y nos aseguramos que se hagan todas las validaciones pertinentes, antes de que lo que sea toque la DB.

    ⚙️ Service¶

    sólo puede ser accedido por la capa controller. Sí o sí, cualquier información de la DB que quiera obtener el controller tiene que ser desde service.

    🎮 Controller¶

    Solo puede ser accedido por la capa controller. O sea que solo puede ser accedida por sí misma. Y a su vez controller puede acceder al resto de capas que no sean repository

    HTTP Request → Controller → Service → Repository → Base de Datos

    📚 Convenciones¶

    🏗️ Entity¶

    🗄️ Repository¶

    A la hora de usar JPA de spring se mantienen una estructura específica y obligatoria. Ya que en la mayoría de casos con jpa solo basta con poner el nombre del metodo, y el resto lo hace spring. Estructura de nombre: "findBy + Propiedad + Operador" Ejemplo: Optional findByEmail(String email);

    Fórmula General¶

    <Prefijo>By<Campo><Operador>
    [And|Or<Campo><Operador>]*
    [OrderBy<Campo>Asc|Desc]?

    * = repetible ? = opcional

    1️⃣ Prefijo (Subject)¶

    findBy
readBy
getBy
queryBy
searchBy
existsBy
countBy
deleteBy
removeBy

    2️⃣ Campo¶

    Debe coincidir exactamente con el nombre del atributo de la entidad (CamelCase).

    Ej: 

    Email
CreatedAt
AuthorId
Status

    3️⃣ Operadores (Predicate)¶

    Comparación: 

    Is
Equals
Not
GreaterThan
GreaterThanEqual
LessThan
LessThanEqual
Between
After
Before

    Texto¶
    Like
Containing
StartingWith
EndingWith
IgnoreCase
    Nulos / Booleanos¶
    IsNull
IsNotNull
True
False
    Colecciones¶
    In
NotIn

    4️⃣ Conectores lógicos¶

    And
Or

    5️⃣ Ordenamiento opcional¶

    OrderBy<Campo>Asc
OrderBy<Campo>Desc

    Ejemplos¶

    // UserRepository
Optional<User> findByEmail(String email);
List<User> findByNameContaining(String name);
List<User> findByCreatedAtBetween(LocalDateTime start, LocalDateTime end);
boolean existsByEmail(String email);
long countByCreatedAtAfter(LocalDateTime date);


// ArticleRepository
List<Article> findByTitleContaining(String title);
List<Article> findByAuthorId(Long authorId);
List<Article> findByAuthorEmail(String email);
List<Article> findByCreatedAtBefore(LocalDateTime date);

//Generic examples:
Optional<User> findByEmail(String email);
List<User> findByNameContaining(String name);
List<User> findByIdGreaterThan(Long id);
List<User> findByCreatedAtBetween(LocalDateTime start, LocalDateTime end);
List<Article> findByAuthorIdAndActiveTrue(Long authorId);
boolean existsByEmail(String email);
long countByActiveTrue();
List<User> findByStatusIn(List<Status> statuses);

    ⚙️ Service¶

    📌 Regla General¶

    Los métodos del Service deben expresar intención de negocio, no consultas de base de datos.

    Formato recomendado:

    verbo + contexto

    (La entidad ya está implícita en el nombre del Service)

    🔹 Verbos comunes¶

    Estos verbos no son reglas del todo estrictas. Mi recomendacion personal es: En caso de que tu tipo de servicio este en la lista, se utiliza el nombre de la lista, y en su defecto se utiliza otro nombre acorde.

    Verbo ¿Qué hace? ¿Cuándo se usa? ¿Qué debería retornar? ¿Puede fallar si no existe?
    create Crea una nueva entidad Cuando se genera un recurso nuevo sin lógica especial de alta La entidad creada ❌ No aplica
    register Crea una entidad con reglas de negocio específicas de alta Cuando el alta tiene validaciones o pasos adicionales (ej: contraseña, email único) La entidad creada ❌ No aplica
    update Modifica una entidad existente Cuando se cambia información de un recurso La entidad actualizada ✅ Sí (si no existe)
    delete Elimina definitivamente una entidad Cuando la eliminación es permanente void ✅ Sí
    remove Quita una relación o realiza una baja lógica Cuando no es eliminación física (ej: quitar rol, desasignar) void ⚠ Depende del caso
    get Obtiene una entidad obligatoriamente existente Cuando debe existir sí o sí La entidad ✅ Sí (lanza excepción si no existe)
    find Busca una entidad que puede no existir Cuando la ausencia no es error Optional<Entity> ❌ No
    list Devuelve múltiples entidades Cuando se espera una colección List<Entity> ❌ No (puede devolver lista vacía)
    search Devuelve múltiples entidades según criterios variables Cuando hay filtros complejos o combinables List<Entity> ❌ No
    activate Cambia estado a activo Cuando existe un flujo de estados void o entidad actualizada ✅ Sí
    deactivate Cambia estado a inactivo Cuando se deshabilita sin borrar void o entidad actualizada ✅ Sí
    publish Cambia estado a publicado Cuando hay lógica de visibilidad o aprobación void o entidad actualizada ✅ Sí
    assign Asocia una entidad con otra Cuando se crea una relación (ej: usuario a rol) void o entidad actualizada ✅ Sí
    login Autentica un usuario Cuando se verifican credenciales para acceder al sistema Token o entidad autenticada ✅ Sí
    authenticate Valida identidad de un usuario Similar a login pero más genérico Token o entidad autenticada ✅ Sí

    🔹 Ejemplos¶

    User register(CreateUserRequest request);
User getById(Long id);
User getByEmail(String email);
List<User> list();
void delete(Long id);

Article create(CreateArticleRequest request);
List<Article> getByAuthor(Long authorId);
Article getById(Long id);

    ❌ Evitar en Service¶

    Nombres técnicos propios del Repository:

    findByEmailAndCreatedAtBetween ❌

    🎯 Resumen¶

    • camelCase
    • Nombres descriptivos
    • Orientado al negocio
    • La entidad está implícita en el Service
    • No exponer detalles de base de datos

    🎮 Controller¶

    📌 Regla General¶

    El Controller se encarga de recibir las solicitudes HTTP y devolver una respuesta al cliente. Es la capa más externa, la que "toca" el usuario.

    Formato recomendado:

    <HTTP Method> + <recurso>

    🔹 Métodos más comunes¶

    GET    → Obtener recursos
POST   → Crear nuevos recursos
PUT    → Actualizar recursos existentes
DELETE → Eliminar recursos
PATCH  → Actualizar parcialmente

    🔹 Anotaciones típicas de Spring¶

    @GetMapping       → Traer datos
@PostMapping      → Crear datos
@PutMapping       → Actualizar datos completos
@DeleteMapping    → Eliminar datos
@RequestBody      → Recibe datos del cliente
@PathVariable     → Obtiene datos de la URL
@RequestParam     → Obtiene parámetros de la URL
@ResponseStatus   → Define el código de estado HTTP

    🔹 Códigos de estado comunes¶

    200 → OK (todo bien)
201 → Created (creado exitosamente)
204 → No Content (sin contenido para devolver)
400 → Bad Request (error del cliente)
404 → Not Found (no encontrado)
500 → Internal Server Error (error del servidor)

    🔹 Ejemplos¶

    @GetMapping
public List<User> getAll() { ... }

@GetMapping("/{id}")
public User getById(@PathVariable Long id) { ... }

@PostMapping
public ResponseEntity<User> create(@RequestBody User user) { ... }

@PutMapping("/{id}")
public User update(@PathVariable Long id, @RequestBody User user) { ... }

@DeleteMapping("/{id}")
public void delete(@PathVariable Long id) { ... }

    ❌ Evitar en Controller¶

    • Lógica de negocio (eso va en Service)
    • Consultas directas a la base de datos (eso va en Repository)
    • Validaciones complejas (delegar al Service)

    🎯 Resumen¶

    • Anotaciones HTTP (@GetMapping, @PostMapping, etc.)
    • Nombres simples y descriptivos
    • Usar ResponseEntity para controlar el código de estado
    • Delegar toda la lógica al Service
    • Solo recibe y responde HTTP
