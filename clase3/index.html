    Clase 3: Recepción de Datos en APIs - Records y Protocolos HTTP¶

    En esta clase profundizaremos en cómo se reciben los datos en una API REST, los tipos de parámetros que podemos recibir, y los métodos HTTP.

    🎯 Tipos de Datos que Recibimos en una API¶

    Spring nos ofrece varias formas de recibir datos, cada una para un contexto específico.

    1. @RequestBody - Cuerpo de la solicitud¶

    ¿Cuándo usarlo?: Cuando el cliente envía datos en el cuerpo del request (POST, PUT).

    @PostMapping
public ResponseEntity<User> create(@RequestBody CreateUserRequest request) {
    // El JSON del body se convierte automáticamente a CreateUserRequest
}

    Contenido típico: 

    {
    "name": "Juan",
    "email": "juan@email.com",
    "password": "micontraseña"
}

    2. @PathVariable - Variables en la URL¶

    ¿Cuándo usarlo?: Para identificar un recurso específico en la URL.

    @GetMapping("/{id}")
public ResponseEntity<User> getById(@PathVariable Long id) {
    // La URL /users/5 → id = 5
}

@GetMapping("/by-author/{authorId}")
public ResponseEntity<List<Article>> listByAuthor(@PathVariable Long authorId) {
    // La URL /articles/by-author/3 → authorId = 3
}

    3. @RequestParam - Parámetros de query¶

    ¿Cuándo usarlo?: Para filtros, búsqueda, paginación. Datos opcionales en la URL.

    @GetMapping
public ResponseEntity<List<Article>> searchByTitle(@RequestParam String title) {
    // GET /articles/search?title=java
}

    4. @RequestHeader - Encabezados¶

    ¿Cuándo usarlo?: Para acceder a headers HTTP (autenticación, idioma, etc.).

    @GetMapping
public ResponseEntity<User> getProfile(@RequestHeader("Authorization") String token) {
    // Accede al header Authorization
}

    📊 Comparativa: ¿Cuándo usar cada uno?¶

    Anotación Datos típicos Ejemplo de URL ¿Obligatorio?
    @RequestBody JSON del recurso POST /users {json} Sí
    @PathVariable Identificador del recurso GET /users/5 Sí
    @RequestParam Filtros, búsqueda GET /users?name=Juan No
    @RequestHeader Metadatos (auth, idioma) Header: Authorization No

    🏗️ Records para Request DTOs¶

    Los record son una forma concisa de crear clases inmutables para transportar datos.

    Sintaxis básica¶

    public record RegisterRequest(String name, String email, String password) {}

    automáticamente genera: - Constructor - Getters (name(), email(), password()) - equals(), hashCode(), toString()

    Ejemplo completo (como en el código de clase)¶

    @RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    public ResponseEntity<User> register(@RequestBody RegisterRequest request) {
        User user = userService.register(request.name(), request.email(), request.password());
        return ResponseEntity.status(HttpStatus.CREATED).body(user);
    }

    @PutMapping("/{id}")
    public ResponseEntity<User> update(@PathVariable Long id, @RequestBody UpdateUserRequest request) {
        return ResponseEntity.ok(userService.update(id, request.name(), request.email()));
    }

    @PostMapping("/login")
    public ResponseEntity<User> login(@RequestBody LoginRequest request) {
        return ResponseEntity.ok(userService.login(request.email(), request.password()));
    }

    // Records como clases internas
    public record RegisterRequest(String name, String email, String password) {}
    public record UpdateUserRequest(String name, String email) {}
    public record LoginRequest(String email, String password) {}
}

    ✅ Validaciones¶

    Las validaciones de tipos y formato van en los DTOs (Records), no en el Service. El Service solo valida reglas de negocio.

    // Controller - simple
@PostMapping
public ResponseEntity<User> register(@RequestBody RegisterRequest request) {
    User user = userService.register(request.name(), request.email(), request.password());
    return ResponseEntity.status(HttpStatus.CREATED).body(user);
}

// DTO - validaciones de formato y obligatoriedad
public record RegisterRequest(
    @NotBlank(message = "El nombre es obligatorio")
    String name,

    @NotBlank(message = "El email es obligatorio")
    @Email(message = "Email inválido")
    String email,

    @NotBlank(message = "La contraseña es obligatoria")
    String password
) {}

// Service - solo reglas de negocio
public User register(String name, String email, String password) {
    if (userRepository.existsByEmail(email)) {
        throw new IllegalArgumentException("El email ya está registrado");
    }

    User user = new User(name, email, password);
    return userRepository.save(user);
}

    ¿Qué va en cada capa?¶

    Tipo de validación Dónde va Ejemplo
    Formato/obligatoriedad DTO @NotBlank, @Email, @Size
    Reglas de negocio Service "email ya existe", "usuario inactivo"

    🔌 Métodos HTTP y sus contextos¶

    GET - Obtener recursos¶

    @GetMapping
public ResponseEntity<List<User>> list()

@GetMapping("/{id}")
public ResponseEntity<User> getById(@PathVariable Long id)

    Cuándo usar GET: Cuando NO modificas datos, solo los recuperás.

    POST - Crear recursos¶

    @PostMapping
public ResponseEntity<User> create(@RequestBody CreateUserRequest request) {
    User user = userService.create(request...);
    return ResponseEntity.status(HttpStatus.CREATED).body(user);
}

    Cuándo usar POST: Para crear nuevos recursos. Respuesta típica: 201 Created.

    PUT - Actualizar completamente¶

    @PutMapping("/{id}")
public ResponseEntity<User> update(@PathVariable Long id, @RequestBody UpdateUserRequest request) {
    return ResponseEntity.ok(userService.update(id, request...));
}

    Cuándo usar PUT: Reemplazar completamente un recurso. Idempotente.

    PATCH - Actualizar parcialmente¶

    @PatchMapping("/{id}")
public ResponseEntity<User> partialUpdate(@PathVariable Long id, @RequestBody PatchUserRequest request)

    Cuándo usar PUT: Actualizar solo algunos campos.

    DELETE - Eliminar recursos¶

    @DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    userService.delete(id);
    return ResponseEntity.noContent().build();
}

    Cuándo usar DELETE: Eliminar permanentemente. Respuesta típica: 204 No Content.

    📋 Códigos de Estado HTTP¶

    Código Significado Cuándo usarlo
    200 OK GET exitoso, PUT/PATCH exitoso
    201 Created POST que crea un nuevo recurso
    204 No Content DELETE exitoso
    400 Bad Request Datos inválidos
    404 Not Found Recurso no encontrado
    500 Internal Server Error Error inesperado

    ⚠️ Errores comunes¶

    1. Exponer Entity directamente en POST¶

    // ❌ MALO - El cliente puede enviar cualquier campo
@PostMapping
public User create(@RequestBody User user) {
    return userService.create(user);
}

// ✅ BUENO - Usar Record para controlar qué se recibe
@PostMapping
public ResponseEntity<User> create(@RequestBody RegisterRequest request) {
    User user = userService.register(request.name(), request.email(), request.password());
    return ResponseEntity.status(HttpStatus.CREATED).body(user);
}

    2. No validar datos¶

    // ❌ MALO - Sin validación
@PostMapping
public User create(@RequestBody RegisterRequest request) {
    // El email puede ser null, vacío...
}

// ✅ BUENO - Validar en Service antes de guardar
public User register(String name, String email, String password) {
    if (name == null || name.isBlank()) {
        throw new IllegalArgumentException("El nombre es obligatorio");
    }
    // ...
}

    📝 Resumen¶

    Necesidad Solución
    Crear usuario @PostMapping + Record + 201
    Actualizar @PutMapping("/{id}")
    Buscar por ID @GetMapping("/{id}") + @PathVariable
    Buscar con filtro @GetMapping + @RequestParam
    Eliminar @DeleteMapping("/{id}") + 204
    Validar En DTOs con anotaciones (@NotBlank, @Email)
