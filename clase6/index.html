    Guía de Commits Profesionales en Git¶

    🧠 Idea base¶

    Un commit no es guardar código. Es contar una historia.

    Un buen commit permite:

    • Entender qué cambió
    • Entender por qué
    • Navegar el proyecto sin contexto previo

    🧩 Regla de oro¶

    1 commit = 1 intención

    Un commit puede tocar muchos archivos, pero debe representar una sola idea.

    ❌ Malo¶

    • "cambios varios"
    • "fix"
    • mezcla de features + bugs + refactor

    ✅ Bueno¶

    • add user validation
    • fix null pointer in user controller
    • refactor order service

    📦 Commits y múltiples archivos¶

    ✔ Es totalmente válido que un commit modifique varios archivos.

    Ejemplo:

    add user creation feature

    Incluye:

    • entity
    • repository
    • service
    • controller

    👉 Está bien porque todo forma parte de una misma feature.

    🧱 Cómo organizar commits en una feature¶

    🟢 Opción simple (recomendada)¶

    Un commit por feature:

    add order service

    Incluye:

    • Service
    • Repository
    • Controller
    • Lo necesario

    🔵 Opción avanzada (commits atómicos)¶

    Separar por pasos lógicos:

    • create order entity
    • add order repository
    • implement order service
    • connect order service to controller

    👉 Más profesional, mejor historial.

    🎯 Cómo decidir¶

    Si cada parte tiene sentido por sí sola → separalo Si todo depende de todo → juntalo

    ✂️ Cuándo hacer commit¶

    • Cuando terminás una unidad lógica
    • Antes de romper algo grande
    • Antes de refactorizar
    • Cuando algo ya funciona
    • Nunca todo al final

    Si te cuesta explicar el commit, hiciste demasiado.

    🧹 Mensajes de commit¶

    📌 Estructura recomendada¶

    verbo + qué + (dónde opcional)

    🔤 Verbos comunes (usar en inglés, imperativo)¶

    ➕ Features¶

    • add
    • implement
    • create

    🐛 Bugs¶

    • fix
    • resolve

    ♻️ Refactor¶

    • refactor
    • simplify
    • clean

    🔧 Cambios varios¶

    • update
    • change

    🧪 Testing¶

    • add tests
    • improve tests

    ✅ Ejemplos buenos¶

    • add login endpoint
    • fix validation bug in user service
    • refactor order repository queries
    • implement payment service
    • create user entity

    ❌ Ejemplos malos¶

    • fix
    • cosas
    • update code
    • varios cambios

    ⚠️ Errores comunes¶

    • Commits gigantes
    • Mensajes vagos
    • Mezclar refactor con features
    • No commitear por miedo

    🧪 Regla práctica¶

    ¿Podrías hacer rollback de este commit sin romper el proyecto?

    • Sí → buen commit
    • No → está mal dividido

    🚧 Trabajo incompleto (WIP)¶

    🟢 Opción 1: WIP commit¶

    wip: user validation logic

    Usar cuando:

    • No terminaste
    • Tenés que cambiar de tarea

    👉 No debería quedar en la historia final.

    🟡 Opción 2: Commit incompleto pero funcional¶

    add basic user validation

    ✔ Mejor opción si:

    • El sistema no se rompe
    • El cambio tiene sentido

    🔵 Opción 3: Stash¶

    git stash

    Luego:

    git stash pop

    Usar cuando:

    • Código roto
    • Experimental
    • No listo para commit

    🟣 Opción 4: Nueva rama (recomendado)¶

    Si cambiás de contexto:

    feature/user-validation
feature/payment-flow

    👉 Evita mezclar cosas.

    🧠 Regla final¶

    Git no guarda archivos. Guarda decisiones.

    Si alguien ve tu commit, ¿le sirve o lo confunde?

    🔥 Resumen rápido¶

    • 1 commit = 1 intención
    • Puede tocar muchos archivos
    • Mensajes claros y específicos
    • Preferir commits funcionales
    • Usar WIP / stash / ramas cuando haga falta

    Este documento sirve como guía práctica para escribir commits claros, profesionales y mantenibles.
